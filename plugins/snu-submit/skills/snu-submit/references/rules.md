# 기록 형식과 판정 규칙

대상: `0.1.0-alpha.1` · `offline-preview`.

이 문서는 호스트 에이전트가 쓰는 기록과 로컬 엔진이 지켜야 할 규칙을 정한다. 로컬 엔진과 JSON 스키마(`assets/schemas/source.json`, `requirements.json`, `checks.json`)는 **예정**이다.
스키마가 생기면 필드 이름·허용 값은 스키마가 우선하며, 이 문서와 다르면 스키마를 따르고 차이를 사용자에게 알린다.
엔진이 아직 구현하지 않은 규칙은 "엔진 요구사항"이며, 구현됐다고 말하지 않는다.

## 1. 실행 디렉터리 (예정 구성)

```text
<작업 위치>/.snu-submit/runs/<run_id>/
  sources/raw/          호스트 도구 원문 출력·다운로드 바이트 (그대로 저장)
  sources/normalized/   엔진이 만든 정규화 텍스트
  source*.json          출처 기록
  requirements.json     요구사항
  selection.json        제출 파일 선택 목록
  coverage.json         수집 범위 기록
  freshness.json        최종 재수집 기록
  report.json / report.html   엔진 출력
```

- `<작업 위치>`는 제출 폴더와 겹치지 않아야 한다. 엔진은 겹치면 어떤 출력도 쓰기 전에 거부해야 한다.
- 지난 실행 디렉터리는 수정하지 않는다. 재검사는 새 실행으로 기록한다.

## 2. 출처 기록 (source)

| 필드 | 내용 |
|---|---|
| `source_id` | 실행 안에서 유일한 ID |
| `kind` | 과제 상세, 공지, 첨부, 연결 문서, 메일, 메일 첨부, 사용자 제공 문서 등 |
| `course_id`, `assignment_id`, `section_id`, `audience` | 화면·원문에서 관찰한 값. 모르면 `"unknown"` |
| `original_url`, `final_url` | 연 주소와 리디렉션 후 주소. 메일은 해당 없음 |
| `observed_at` | 수집 시각(시간대 포함 ISO 8601) |
| `raw_ref` | `sources/raw/` 아래 실제 원문 파일 상대 경로 |
| `raw_sha256` | 원문 바이트 해시 — **엔진이 계산**, 모델은 비워 둔다 |
| `normalized_ref`, `normalized_sha256`, `normalization_version` | 엔진이 정규화한 텍스트와 그 해시·버전 |
| `collection_status`, `collection_reason` | `complete` / `partial` / `failed`와 이유(잘림, 접근 거부, 로딩 미완료, 인증 만료 등) |
| `locations` | 페이지·문단·표 셀 등 위치 정보(가능한 경우) |
| `issued_at`, `modified_at` | 원문에 보이는 게시·수정 시각. 없으면 `"unknown"` |
| `unread_regions` | 이미지·스캔·읽지 못한 첨부 등 텍스트로 읽지 못한 부분 |

- 참조 경로는 실행 디렉터리 안이어야 하며 링크(심볼릭 링크·정션)를 허용하지 않는다.
- 엔진은 `check`와 `recheck` 때마다 원문 파일을 다시 읽어 해시를 대조해야 한다. 불일치·누락이면 그 출처에 기댄 요구사항은 거부 또는 `unknown`이고 준비됨 판정을 금지한다.

## 3. 요구사항 기록 (requirement)

| 필드 | 내용 |
|---|---|
| `requirement_id` | 유일한 ID |
| `source_id` | 존재하는 출처 ID |
| `quote` | 정규화 텍스트에서 그대로 복사한 인용문 |
| `span` | `{start, end}` — 정규화 텍스트의 Unicode 코드 포인트 위치. `normalized_text[start:end] == quote`여야 함 |
| `location` | 페이지·문단 등(의미 있을 때) |
| `axis` | `instructor_requirement`(교수자 요구) 또는 `system_constraint`(제출 화면 형식·기간 제약) |
| `applicability` | 강의·과제·분반·대상 일치 여부: `applies` / `not_applicable` / `unknown` |
| `mandatory` | 필수 여부 |
| `check` | `kind`, `operator`, `value`, `unit` 과 대상(아래 5절) |
| `state` | `confirmed` / `ambiguous` / `conflict` |
| `supersedes` | 명시적 정정일 때만: 대체되는 요구사항 ID와 정정 근거 출처·인용 |
| `user_confirmation` | 사용자 확인 증거(별도 기록, 4절 참고) |

- 요구사항은 **데이터**다. Python, 정규식, 셸 명령, 도구 지시를 넣지 않는다. 지원하지 않는 `kind`/`operator`/수량 표현, 추가 필드, 중복 ID, 존재하지 않는 출처 ID, 유한하지 않은 숫자는 엔진이 거부해야 한다.
- 인용·구간·해시가 맞지 않거나 이미지 등 읽지 못한 영역에 기댄 요구사항은 근거로 인정하지 않는다.
- 과제 본문이 비어 있거나 요구사항이 0개라도 "조건 없음"이 아니다. 수집 범위 경고와 함께 `확인 필요`다.

### 지원 예정 검사 종류

| 종류 | 방법 | 비고 |
|---|---|---|
| 파일 존재·개수, 이름(정확/안전한 glob), 확장자·실제 형식, 바이트 크기 | deterministic | 형식은 확장자가 아니라 파일 서명과 파서로 판단 |
| PDF 페이지 수 | deterministic | 페이지 수는 내용 완전성을 뜻하지 않음 |
| ZIP 내부 항목 존재 | deterministic | 내부 경로와 외부 경로를 분리 |
| DOCX 표 존재 | deterministic | 셀 위치 기록. DOCX 쪽수·레이아웃은 `unknown` |
| 글자 수·단어 수 | deterministic | 단위가 명확히 정의된 경우만. 한국어 글자 수 관례가 불명확하면 `unknown` |
| 특정 내용 포함(의미 판단) | content_review → user_confirmed | 후보 위치는 보여 줄 수 있으나 사용자 확인 전까지 `unknown` |
| 마감·제출 기간 | 별도 축 | 파일 준비 상태와 섞지 않음 |

- 크기 단위가 `MB`처럼 10진/2진이 불명확하면 두 해석 모두에서 통과일 때만 `pass`, 두 해석 모두에서 위반일 때만 `fail`, 그 사이는 `unknown`이다.
- 비교 경계(미만/이하/초과/이상)는 원문 표현대로 기록한다. 불명확하면 `ambiguous`.

## 4. 사용자 확인 (user_confirmed)

- 의미 판단 항목은 특정 요구사항에 대해, 사용자가 특정 파일·위치를 보고 확인했다는 기록(요구사항 ID, 파일 ID와 해시, 위치, 확인 문구, 시각)이 있을 때만 `pass`가 될 수 있다.
- "다 괜찮아" 같은 일괄 승인은 어떤 항목도 바꾸지 못한다. 사용자 확인으로 접근 실패·파싱 실패·해시 불일치를 지울 수 없다.
- 확인한 뒤 파일 해시가 바뀌면 확인은 무효다.

## 5. 제출 파일 선택과 대상 지정

### selection manifest

- `submission_root`와 제출 파일 목록 `files: [{file_id, relative_path, role}]`. 역할 예: `report`, `appendix`, `code`, `data`, `archive`, `other`.
- 안내문·참고 자료·이전 보고서는 `excluded`에 이유와 함께 두고 제출 집합에 넣지 않는다.
- 후보가 모호하면(초안/최종본, 같은 이름 다른 폴더) 최신 파일을 고르지 않는다. 사용자가 고를 때까지 선택은 `unknown`이다.
- 엔진은 선택 목록 자체의 해시와 각 파일의 상대 경로·크기·SHA-256을 기록해야 한다.

### target

| 필드 | 값 |
|---|---|
| `target_scope` | `submission_set` / `file` / `archive_entry` |
| `selector` | 역할(`role`), 정확한 이름(`exact_name`), 안전한 glob(`glob`), 또는 아카이브 선택자 + 정확한 내부 경로(`entry_path`) 중 하나 |
| `cardinality` | `{min, max}` |
| `quantifier` | `each` / `all` / `exists` |

- glob은 상대 이름 패턴만 허용한다. 절대 경로, 드라이브 문자, `..`, 역슬래시 모호성, 폴더 밖을 향하는 패턴은 거부한다.
- 검사 결과의 대상은 실제로 해석된 파일 ID와 실제 해시를 가진다. 없으면 `missing_target`(기대 역할·이름·경로)이며 해시를 지어내지 않고 다른 파일로 대체하지 않는다.
- 집합 검사는 파일 ID가 없어도 되지만 선택 목록 해시·파일 목록·개수를 참조한다.
- 예: 6쪽 보고서는 별도의 1쪽 참고 파일이 5쪽 제한을 통과한다고 해서 통과하지 않는다. ZIP 안에 같은 이름의 부록이 있어도 외부 부록 파일 요구사항을 대신하지 않는다.

## 6. 상태와 종합 판정

- 항목 상태: `pass` / `fail` / `unknown` / `not_applicable`. 방법: `deterministic` / `content_review` / `user_confirmed`.
- 종합 판정 (위에서부터 먼저 해당하는 것):
  1. 필수 항목에 확인된 `fail`이 있으면 `수정 필요`. `unknown` 개수를 함께 표시한다.
  2. 필수 `unknown`, 수집 범위 미완료, 해결되지 않은 충돌·적용 대상·날짜·파일 선택, 파싱 실패, 예산 초과, 오래된 출처 중 하나라도 있으면 `확인 필요`.
  3. 비어 있지 않은 필수 조건이 모두 평가됐고 위반·`unknown`이 없을 때만 `확인된 요구사항 기준 파일 준비됨`.
- 준비됨은 실제 제출 가능 여부, 서버 접수, 답안 품질을 뜻하지 않는다.
- 로컬 준비 모드(같은 실행 안의 최신성 재수집 기록이 없음)에서는 출처 최신성이 `unknown`이므로 3번에 도달할 수 없다.
- offline-preview 단계에서는 3번에 도달하더라도 "현재 온라인 기준 제출 준비 완료"로 표현하지 않는다.
- 가상 예제(`가상 과제 재현`)에서는 기계적 통과를 보여 줄 수 있지만 실제 eTL 준비 상태로 표시하지 않는다.

## 7. 충돌, 정정, 적용 대상

- 명시적 정정("~로 정정합니다")은 강의·과제·분반·대상이 같을 때만 이전 요구사항을 대체한다. 이전·새 근거를 모두 보존한다.
- 정정 표현 없이 서로 다른 값이 있으면 게시 시각이 더 늦어도 이기지 않는다. `conflict`로 남기고 `확인 필요`.
- 다른 분반·다른 강의의 공지는 적용하지 않는다(`not_applicable`). 분반·대상을 판단할 수 없으면 `unknown`.
- 개인별 연장, 조별 과제 적용 여부는 근거로 해결될 때까지 `unknown`.
- 메일만으로 현재 요구사항을 확정하지 않는다. 메일은 발견·이력 근거이며, 같은 내용을 eTL에서 확인하지 못하면 `unknown`이다.
- 교수자 요구(`instructor_requirement`)와 제출 화면 제약(`system_constraint`)은 다른 축이다. 둘이 충돌하면(예: 마감 시각, 허용 형식) 둘 다 보이게 남긴다.

## 8. 날짜와 시간

- 원문 표현을 그대로 보존한다("다음 주 금요일 자정", "10/31").
- 연도와 시간대 근거가 있을 때만 `Asia/Seoul` 절대 시각으로 정규화한다. 상대 날짜·연도 없는 날짜는 근거나 사용자 확인으로 해결될 때까지 `unresolved`이며 수집 범위는 미완료다.
- 제출 기간 상태(`open` / `locked` / `unknown`)와 화면에서 관찰한 서버 제출 상태는 파일 준비 상태와 별도로 보고한다.
- 서버에 같은 이름의 파일이 있어도 로컬 파일과 같은 바이트라는 뜻이 아니다. 마감·잠금 뒤 "지금 제출 가능"이라고 하지 않는다.

## 9. 수집 범위 (coverage)

미완료 사유 중 하나라도 있으면 수집 범위는 `incomplete`다.

- 학기 시작일을 근거로 확인하지 못함, 또는 학기 시작 무렵의 공통 안내(이름 규칙·서약서 등)를 읽지 못함
- 공지 목록 5페이지 또는 100건 한도에 걸려 나머지가 남음, 다음 페이지가 있는데 읽지 않음
- 고정·공통 공지를 확인하지 못함
- 요구사항이 걸린 첨부·연결 문서를 받지 못함(메일에 MIME 첨부가 없어도 본문 링크 문서는 필요)
- 인증 만료, 접근 거부, 로딩 미완료, 본문 잘림
- 날짜 미해결, 이미지·스캔 등 읽지 못한 영역

기록할 것: 학기 시작일과 근거, 확인 기간(학기 시작 ~ 검사 시각), 읽은 목록 페이지 수와 건수, 다음 페이지 유무, 한도 도달 여부, 고정·공통 공지 확인 여부, 필요한 첨부·연결 문서와 받은/실패한 항목, 실패 이유.

## 10. 최신성 (freshness)

- 현재 출처 기준 결론 전, 같은 실행 안에서 과제 상세·관련 현재 공지·필수 첨부를 다시 읽고 해시를 비교한다(URL이 같아도 바이트가 바뀔 수 있다).
- 기록: 재수집 시각, 항목별 이전/현재 해시, `fresh` / `changed` / `failed`.
- 마지막 수집이 10분보다 오래됐거나 연결·접근에 실패하면 최신성은 `unknown`.
- 로컬 엔진은 네트워크에 접속하지 않는다. 로컬 전용 재검사는 온라인 최신성을 확인할 수 없다.

## 11. 재검사 (recheck)

- 이전 실행의 파일·출처 해시와 현재 바이트를 비교한다. 바뀐 바이트, 이름 변경, 누락, 추가를 구분한다.
- 바뀐 파일·출처에 영향받는 항목은 무효로 하고 현재 바이트로 다시 평가한다. 이전 `pass`를 그대로 재사용하지 않는다.
- 검사 도중 파일이 바뀌면(검사 전후 stat·해시 불일치) 그 파일의 결과는 `unknown`이다.
- 지난 스냅샷은 수정하지 않는다.

## 12. 로컬 검사 안전 규칙 (엔진 요구사항)

- 제출 폴더 밖으로 나가지 않는다. Windows 대소문자 무시, 정션·재분석 지점, 심볼릭 링크를 고려하고 따라가지 않는다.
- 원본을 수정하지 않는다. ZIP은 파일 시스템에 풀지 않고 제한된 스트림으로만 읽는다. 학생 코드를 실행하지 않는다.
- PDF: 서명 확인과 실제 파싱, 암호화 처리, 페이지 수, 읽지 못한 영역. 빈·손상·암호화·스캔 PDF로는 내용 통과를 만들지 않는다.
- DOCX: 제한된 ZIP/OOXML 구조 검증, 외부 엔티티를 해석하지 않는 XML 파싱, 문단·표 셀 위치, 이미지는 읽지 못한 영역.
- ZIP: 경로 이탈·절대 경로·드라이브·역슬래시 모호성 이름, CRC, 실제 읽은 바이트, 중첩 아카이브를 확인. 암호화·손상·중첩·압축 폭탄·예산 초과는 `unknown`, 필수 항목 누락은 `fail`.
- 텍스트: 인코딩을 명시. HWP/HWPX 등 지원하지 않는 형식의 내용은 `unknown`, 이름·형식·크기·존재 검사만 가능.

### 제품 자원 예산 (과제 제출 한도가 아님)

| 항목 | 기본값 |
|---|---|
| 파일 하나 | 50 MiB |
| 선택 파일 합계 | 200 MiB |
| ZIP | 1,000 항목 / 실제 압축 해제 읽기 200 MiB |
| 문서 페이지 | 300쪽 |
| 파서 시간 | 파서당 30초 (별도 프로세스, 시간 초과 시 정리) |

예산 초과는 해당 항목을 `unknown`으로 만들 뿐이며, 보고서에서 과제의 크기 제한 위반으로 표시하지 않는다.

## 13. 보고서

- JSON이 기준이고 HTML은 같은 내용이다. HTML은 인라인 CSS만 쓰고 스크립트·외부 글꼴·이미지·분석 도구·네트워크 요청이 없다. 파일 이름·인용·URL·속성 값은 모두 이스케이프하고 위험한 링크 스킴을 클릭 가능하게 만들지 않는다.
- 포함 항목: 스키마·도구·규칙 버전, 실행 ID, 시각, 출처 해시, 선택 목록과 해시, 수집 범위와 `unknown` 이유, 항목별 근거, 수정 방법, 스냅샷 한계 안내.
